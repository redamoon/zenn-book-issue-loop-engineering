# child-issue-template: 過去の落とし穴

Sub-issue1〜3（`GET /api/items`実装 → 一覧画面 → キーワード検索）を実際に切った際に
見つかった、テンプレートだけでは防げなかった手戻りの記録。次にSub-issueを書くときの
「範囲」「触ってよいファイル」「完了条件」に先回りで書き足す材料として使う。

## プロジェクト基盤が存在しない状態でのゼロイチ実装

ゼロからの新規機能で、`package.json` / `tsconfig.json` / テストランナーのような
プロジェクト基盤自体が存在しない場合、「触ってよいファイル」に実装対象だけを書いても
実装が完結しない。最小限セットアップをそのSub-issueの範囲に含めるか、別Issueに
切り出すかを、Sub-issueを切る時点で決めておく。決めていないと、Validate段階で
致命的な矛盾として差し戻される。

## Server Componentから自分自身のAPIを呼ぶ方式

Next.js App RouterのServer Componentから、同じアプリの `app/api/**` を呼ぶ場合、
Client Component化するか、絶対URLを構築するかの選択が発生する。範囲か「決定」欄に
どちらを採るか書いておかないと、実装セッションでその都度質問が返ってくる。

## テスト用依存の追加可否

コンポーネントテストに `jsdom` や `@testing-library/react` のような依存が必要になる
ことがある。「触ってよいファイル」に `package.json` を含めるかどうかで、追加してよいかを
先に決めておく。

## fetch失敗と0件の混同

一覧取得のfetchが失敗した場合に、エラーを握りつぶして「該当する結果がありません」と
誤表示する実装が実際に紛れ込んだ（Sub-issue2のcode-reviewで指摘）。完了条件に
「検索結果0件」の挙動だけでなく、「fetch失敗時の挙動」も分けて書く。
