一般的な観点（バグ、簡潔化、効率）は、組み込みの `/code-review`（例: `medium`）に任せる。
このSKILLは、それに加えて、このプロジェクトでしか通用しない契約・規約だけを最小限の
チェックリストとして渡す。レビュー役はRead/Grepのような閲覧専用ツールに絞り、
編集はしない。指摘と修正を別の役目のまま保つ。

## このプロジェクト固有のチェック

- **レスポンス型の契約**: `lib/items/types.ts` の `Item` 型・レスポンス型は
  バックエンド（`app/api/items/route.ts`）とフロントエンド（`app/items/page.tsx` 等）の
  契約。この型を変更するPRが、Sub-issueの「触ってよいファイル」に `types.ts` を
  含んでいるかを確認する。
- **fetch失敗と0件の混同**: 一覧取得やAPI呼び出しの失敗時に、エラーを握りつぶして
  「該当する結果がありません」のような0件表示にしていないか。正常系（検索結果0件）と
  異常系（fetch失敗）を区別しているかを確認する（過去に実際に指摘が出た箇所）。
- **既存APIの契約破壊**: `app/api/items/route.ts` のクエリパラメータ処理や
  `lib/items/repository.ts` の絞り込みロジックを変更するPRが、`keyword` 未指定時に
  全件を返すという既存の挙動を壊していないか。
- **テストの配置**: 変更した挙動に対応する自動テストが `__tests__/api/items.test.ts`
  （API）や `__tests__/items-page.test.tsx`（画面）のような既存の配置ルールに沿って
  追加されているか。Vitestで実行できることを確認する（`npm test`）。
- **CLAUDE.mdとの整合**: プロジェクトの`CLAUDE.md`に書かれたアーキテクチャの説明
  （`route.ts`/`repository.ts`/`types.ts`/テストファイルの役割）が、実際のファイル構成と
  乖離していないか。乖離していれば指摘する（ドキュメント更新の指摘であり、実装の
  バグではない）。

## 使い方

1. まず組み込みの `/code-review medium` を実行し、一般的な指摘を先に出す。
2. 上記のプロジェクト固有チェックを、指摘があれば深刻度付きで追加する。
3. 指摘は箇条書きで返し、修正は実装側（別の役目）に委ねる。
